# 项目代码通用规则

适用范围：本项目全部源代码。新增或修改代码时按本规则执行。

## 一、命名规范

### 1.1 文件与目录名

- 文件名使用**小驼峰（lowerCamelCase）**，如 `userService.ts`、`gradeQuiz.py`、`quizEngine.js`。
- 目录名同样使用小驼峰，如 `utils/`、`common/`、`quizEngine/`。
- 文件名必须能表达文件职责，禁止 `test2.ts`、`新建文件.ts`、`a.js`、`temp.ts` 这类无意义命名。
- 一个文件只承担一个主要职责；文件过大时按职责拆分，而不是继续堆叠。
- 测试文件名与被测文件对应，如 `userService.test.ts` 对应 `userService.ts`。

### 1.2 函数与方法名

- 使用**小驼峰**，以动词或动词短语开头：`getUserInfo()`、`calculateScore()`、`saveQuizResult()`。
- 返回布尔值的函数加 `is` / `has` / `can` / `should` 前缀：`isValid()`、`hasPermission()`。
- 事件处理函数加 `on` / `handle` 前缀：`onSubmit()`、`handleClick()`。
- 禁止用 `doIt()`、`process()`、`data()` 这类含义模糊的名字。

### 1.3 变量与参数名

- 使用小驼峰，名词或名词短语：`userName`、`maxScore`、`questionList`。
- 布尔变量加 `is` / `has` / `can` 前缀；**禁止否定式命名**（`isNotReady`、`isNoError` 一律不用）。
- 禁止拼音命名，禁止无惯例缩写（`usrNm`、`qty` 之类不写）。

### 1.4 类、接口、枚举、类型名

- 使用**大驼峰（UpperCamelCase）**：`class UserService`、`interface QuizResult`、`enum QuestionType`、`type ScoreMap`。
- 类名用名词，不用动词；避免 `Data`、`Info`、`Manager` 这类过于宽泛的词单独作类名。

### 1.5 常量与枚举值名

- 使用**全大写 + 下划线**：`MAX_RETRY_COUNT`、`DEFAULT_TIMEOUT_MS`。
- 枚举值名同样全大写加下划线：`enum UserType { TEACHER = 0, STUDENT = 1 }`。
- 代码中禁止出现无注释说明的「魔鬼数字」，一律提取为具名常量。

### 1.6 命名通用禁令

- 禁止单字母命名，循环变量 `i`、`j` 除外。
- 名称长度控制在 3~30 个字符，过短无意义、过长难读。
- 同一概念在全项目内必须使用同一个词，禁止 `user` 与 `usr`、`list` 与 `arr` 混用。

## 二、注释规范

### 2.1 必须写注释的场景

**复杂函数**——满足以下任意一条即视为复杂，必须写函数级注释：

- 函数体超过 20 行；
- 存在 2 层以上嵌套；
- 包含非直观的算法、公式、位运算或正则表达式；
- 存在副作用（修改全局状态、发起网络请求、读写文件、操作数据库）；
- 参数超过 3 个，或参数含义容易混淆。

**其他必须注释的场景**：

- 所有对外导出的函数、类、常量（公共 API）；
- 为绕开某个缺陷而写的临时方案——必须写明原因和可移除条件；
- 业务规则中的特殊取值、边界条件、兼容性处理。

### 2.2 函数注释格式

统一包含四部分：用途、参数、返回值、异常与副作用。

```ts
/**
 * 按评分要点对简答题作答做关键词初筛打分。
 *
 * @param answer 学习者原文作答，空串视为未作答
 * @param rubric 评分要点列表，各项 score 之和应等于题目总分
 * @returns 初筛得分与是否需要人工复核的标记
 * @throws 当 rubric 结构非法时抛出错误
 * @remarks 关键词命中属于保守判定，命中不全时必须转语义复核，不可直接定分
 */
function gradeShortAnswer(answer: string, rubric: RubricItem[]): Verdict {}
```

### 2.3 注释写法要求

- 注释解释**为什么这么做**，而不是复述代码在做什么。
- 行内注释放在被说明语句的上方或行尾，缩进与代码保持一致。
- 注释必须与代码同步修改；改代码不改注释视为缺陷。
- 禁止：注释掉的死代码、无负责人的 `// TODO`、`// 定义变量 x` 这类废话注释。

## 三、函数设计

- 单一职责：一个函数只做一件事，函数名应能完整概括它的行为。
- 长度不超过 50 行；超过则按职责拆分。
- 参数不超过 4 个；超过时改用对象参数，并为其定义类型。
- 嵌套不超过 3 层；用提前返回（guard clause）替代深层 `if` 嵌套。
- 避免隐藏副作用；确需副作用时必须在注释中声明。
- 无状态依赖的逻辑优先写成纯函数，便于测试。

## 四、代码格式

- 缩进使用空格，禁止 Tab；JS/TS/ArkTS 用 2 空格，Python 用 4 空格。
- 单行宽度不超过 120 个字符。
- 字符串统一使用单引号（按语言惯例，如 Python 无强制要求）。
- 语句结束符保持全项目统一（JS/TS 统一加分号）。
- 一个语句占一行，不把多个变量声明或赋值写在一行。
- 关键字与括号之间保留空格，运算符两侧保留空格。
- 左大括号不另起一行；`else` / `catch` 与前一代码块的右大括号同行。
- 逻辑不相关的代码块之间空一行。

## 五、错误处理

- 只在系统边界做校验：用户输入、外部接口、文件与网络操作。
- 禁止空 `catch`；捕获后必须处理、记录或向上抛出。
- 错误信息必须包含上下文：哪个操作、哪个参数、期望值是什么。
- 内部调用之间不做冗余防御，信任框架与内部约定的保证。

## 六、提交前检查

- 本地跑通 lint 与全部测试再提交。
- 新增或修改的逻辑必须补充对应测试。
- 清除调试代码：`console.log`、`print`、断点、临时注释掉的代码块。

---

## 附：命名风格的适用范围说明

本规则约定文件名使用小驼峰。在 HarmonyOS / ArkTS 生态中，官方示例与部分团队习惯将文件名写作「小写 + 下划线」（如 `user_service.ets`），与本规则不一致。若项目需要与官方示例保持统一，可仅将**文件名**改为下划线风格，函数名、变量名、常量名的规范两者一致，无需改动。
